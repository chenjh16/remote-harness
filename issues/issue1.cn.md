# Issue 1 — 共享服务器账号下反向隧道端口（及别名）冲突

## 现象

当**多个真实用户**同时登录同一个服务器账号，且各自跑 remote-harness 的**反向**流程连回自己的笔记本时，他们的反向隧道会冲突：`RemoteForward <PORT> 127.0.0.1:22` 的端口相撞；更危险的是，服务器端的 ssh 别名被串线，导致一个用户的构建/提交跑到了**另一个用户的笔记本**上。

这是**反向模式特有**的问题。正向模式下，每个用户在*自己*的机器上跑代理、改*自己*的 `~/.ssh/config`；共享服务器只是被 sshfs 读取 + `ssh server 'cd … && build'`，没有共享的按用户状态会冲突。而反向模式下，所有真实用户共用一个服务器账号，所有服务器端状态都落在同一个 `$HOME` 下。

## 冲突点（修复前）

1. **反向端口。** `detect.sh` 给每个并发用户的 `SUGGESTED_PORT` 都一样（"以 22 结尾的最高空闲端口"）。两条隧道都没起来之前，两台笔记本都去绑同一个端口，失败者的 `ssh -N` 因 `ExitOnForwardFailure yes` 退出。
2. **服务器端别名——危险的那个。** `BOX_ALIAS` 默认是 `<笔记本用户名>-mac`。两个笔记本用户名相同（`ubuntu`、`user`、相同的公司用户名）的人，都会把 `Host <名字>-mac` 写进**共享的** `~/.ssh/config`——同一个托管块，谁后跑谁就把它指向自己。而注入的规则会直接执行 `ssh <别名> 'cd <路径> && build/commit/push'`，所以别名被改指就意味着**跨用户代码执行 + 数据泄露**。
3. **默认挂载点 + 会话目录。** 默认 `<HOME>/work/<项目>`；相同的共享 `$HOME` + 相同项目名 → 相同挂载点 → 第二次挂载撞 `not-empty`，`inject-rule.sh` 按挂载点划分的会话目录也跟着撞。
4. **`~/.ssh/config` 读-改-写竞态。** `setup-tunnel.sh` 做 备份→awk→mv，没有加锁；共享账号上的并发运行可能丢失更新。
5. **`known_hosts_<别名>`** 以共享别名命名 → host-key 不匹配的告警噪音（第 2 点的副作用）。

## 考虑过的三个想法

- **启动目录 → 真实用户名（主）。** 在 `~/<名字>/…` 软约定下，`$PWD` 在 `$HOME` 下的第一层路径名按人唯一。注意：它可能是通用目录（`work`/`src`），或 cwd 本身就是 `$HOME`，所以必须*预填一个确认*，绝不自动决定。
- **公钥 comment → 身份（次）。** 服务器端"是哪台笔记本"的精确信号，是*本次入站会话*所用的公钥——从 `$SSH_USER_AUTH` 文件读取（sshd 在 `ExposeAuthInfo yes` 下把本次会话的认证行写进该文件；环境变量里是文件**路径**，不是内容），再去 `authorized_keys` 里匹配并读出 comment。但这需要 `ExposeAuthInfo yes`（默认关），所以常常拿不到。适合做预填，不能当唯一来源。
- **同一用户、多个项目 → 复用一个 rport（正确目标）。** 隧道是 *(笔记本, 服务器账号)* 这一对的属性，不是项目的属性——一个 `RemoteForward` 端口可承载任意多个 sshfs 挂载。规则：**端口 + 别名按真实用户（稳定）；挂载点 + 会话按项目。**

## 修复方案（已实现）

引入一个经确认的**按真实用户命名空间 `RU`**，把它贯穿到别名 + 端口。

- **`detect.sh`** 现在输出 `REALUSER_GUESS` / `REALUSER_SOURCE`
  （`authkey|cwd|authorized_keys|none`）/ `REALUSER_CANDIDATES`，按优先级取自：会话登录所用公钥的**完整 comment**（如 `alice@macbook`——每台机器最唯一的身份；其本地部分 `alice` 作为备选候选）→ `$HOME` 下启动目录第一层路径名（跳过通用名）→ authorized_keys 猜测。`SUGGESTED_PORT` 现在由 `REALUSER_GUESS` 哈希到 `[20022, 29922]`（临时端口下界以下）的一个**稳定 `.22` 槽位**并探测空闲端口，使不同用户落在不同端口、同一用户重连落在同一端口；无命名空间时退回旧的"最高空闲 `.22`"。
- **确认（`reference/reverse.md` 的 Step 0a）。** 代理让用户确认 `RU`（用 `REALUSER_GUESS` 预填，提供候选 + 自由输入）。这是唯一新增的必需确认——已加入 SKILL.md 的"确认，不推断"清单。
- **`setup-tunnel.sh`** 接受 `--namespace <RU>`，当不给 `--port` 时按与 `detect.sh` 相同的方式（公式保持同步）从 `RU` 推导稳定端口并探测空闲槽位。服务器端别名为 `<RU>-mac`。给 `--port` 时仍以它为准（运行时换端口路径）。对共享 `~/.ssh/config` 的写入现在用 `flock` 串行化（尽力而为：flock → mkdir 自旋锁 → 不加锁），使并发 setup 不互相覆盖托管块。
- **`preflight.sh`** 带 `--alias <RU>-mac` 时**只**考虑该命名空间隧道用于复用，因此共享账号上绝不会误连别人的回环别名。`PREFLIGHT=ok` 同时是**同一用户 / 另一个项目**的复用路径（在现有隧道上重新挂载——不需要新端口）。
- **`laptop-setup.sh` 的清理**对共享隧道做引用计数，使同一用户的多项目会话可以任意顺序退出。它把隧道的 `ssh -N` pid 记到 `~/.remote-harness/.tunnel-<box>-<port>.pid`，退出时**仅当**盒子上不再有其它会话的 `<RU>-mac:` sshfs 挂载时才断隧道；最后一个退出的会话通过该 pid 文件断隧道，无论隧道是谁建的。（没有这一步的话，*建*隧道的那个会话退出时把隧道杀掉，会让其它项目的挂载变成悬空。）
- **挂载点**按维护者的决定保持不变：默认用代理当前所在项目目录，校验它是否为空/适合 sshfs，并始终提供手动输入选项。遵守 `~/<名字>/…` 约定时，cwd 本身就带上了命名空间。笔记本项目目录用交互式输入选择。

## 残留限制

- 命名空间的好坏取决于确认：若两个用户都把*同一个*通用猜测当作 `RU` 接受，他们的别名/端口仍会冲突。修法是重跑 Step 0a 给出不同名字；`laptop-setup.sh` 里的运行时换端口仍是兜底。
- 哈希区间假设临时端口下界高于 `29922`（默认 Linux/macOS 成立）；若某机器把它降到该值以下，`detect.sh`/`setup-tunnel.sh` 退回旧的扫描逻辑。
- key-comment 身份识别需要 sshd `ExposeAuthInfo yes`（默认关）。它暴露的是 `$SSH_USER_AUTH`——一个临时文件的**路径**，文件里是本次会话的认证行（`publickey <type> <base64>`）；`detect.sh` 读该文件、把 blob 去 `authorized_keys` 匹配、取**完整** comment（最唯一）。关着时由 cwd 约定承载命名空间——没有可移植的办法在不开该选项的情况下得知本次会话用了哪个 key。
- 共享隧道的引用计数靠在盒子 mount 表里匹配 `<RU>-mac:` 来识别其它挂载——这是 **Linux** 信号。在 macOS/FUSE-T 盒子上挂载源不是 `<alias>:path`，识别不到其它挂载，于是隧道仍会在第一个会话退出时被断。某次崩溃、没来得及写 pid 文件而遗留的隧道同样不会被自动回收（重跑 remote-harness 会在同一稳定端口重建并重挂）。
